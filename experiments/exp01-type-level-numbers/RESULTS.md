# EXP-01: Type-level natural numbers — RESULTS

**Tests:** R12's assumption that stable Rust can express naturals in types,
with decrement and constant values, at useful sizes.

- Toolchain: `rustc 1.98.1 (48a229cea 2026-09-01) (Homebrew)`, `cargo 1.98.1`, stable channel, macOS (Darwin 24.6.0, Apple Silicon).
- Dependencies: none at build time; `trybuild = "1"` as dev-dependency for compile-fail tests, as allowed by the common protocol.
- Final state: everything compiles; `cargo test` passes — 13 unit tests plus 6 trybuild compile-fail cases with pinned `.stderr` files.

## Measurements

Method: for each encoding and N, `measure/measure.py` generates a minimal
self-contained crate (no dev-deps) containing the encoding, aliases up to N,
a `const TOP: u64 = N::VALUE;` to force full evaluation, and a type-equality
proof that N/2 + N/2 == N. It bisects the smallest `#![recursion_limit]`
that compiles, then runs `cargo clean && cargo build` three times and takes
the median (wall clock). Order of magnitude is what matters, per protocol.

| Encoding | N | Aliases-only compiles at default limit (128)? | Minimal `recursion_limit` to *use* N | Median clean build (3 runs) |
|---|---|---|---|---|
| Peano | 10 | yes | 13 (default enough) | 1.05 s |
| Peano | 100 | yes | 103 (default enough) | 1.02 s |
| Peano | 500 | yes | **503** (default NOT enough) | 1.64 s |
| Peano | 1000 | yes | **1003** (default NOT enough) | 4.60 s |
| Binary | 10 | yes | 7 (default enough) | 1.06 s |
| Binary | 100 | yes | 10 (default enough) | 1.13 s |
| Binary | 500 | yes | 12 (default enough) | 1.03 s |
| Binary | 1000 | yes | 13 (default enough) | 1.07 s |

Observations:

- **Defining** aliases is lazy and free: even `N1000` as a pure alias
  compiles at the default limit. The cost lands where a number is *used* —
  evaluating `VALUE` or solving a trait bound.
- Peano needs `recursion_limit` ≈ **N + 3**; binary needs ≈ **bits(N) + 3**.
  The attribute is *per crate*, so every downstream crate that touches deep
  Peano numbers must set it, not just the library that defines them.
- Peano compile time is flat to N≈500 and visibly superlinear after
  (~1 s baseline → 4.6 s at N=1000, dominated by one `VALUE` use and one
  addition). Binary is flat (~1 s) throughout. Neither is anywhere near
  "minutes" at N=1000, but a model with *many* distinct large Peano numbers
  would multiply the 4.6 s figure.
- The full experiment crate (both encodings, all 2002 aliases,
  `recursion_limit = "2048"`, no deep `VALUE` use in the lib itself):
  `cargo clean && time cargo build` → 1.59 s / 1.57 s / 1.58 s, median **1.58 s**.

## Ergonomics

- **With aliases**, both encodings are pleasant: `N42`, `BN42`,
  `<N42 as Pred>::Out`, `<BN500 as Add<BN500>>::Sum`. No practical
  difference between encodings at the point of use.
- **Without aliases**, Peano is unusable beyond ~5
  (`Succ<Succ<Succ<Succ<Zero>>>>` is already the limit of comfortable
  reading; N42 is a 42-deep nest). Binary is *writable* at any size
  (`UInt<UInt<UInt<UInt<UInt<UInt<UTerm, B1>, B0>, B1>, B0>, B1>, B0>` = 42)
  but inside-out, MSB-first, and easy to get silently wrong — a
  transposition produces a different valid number, not an error. The
  `uint!(1 0 1 0 1 0)` helper macro makes hand-written binary tolerable.
- **Aliases leak away in errors.** Compiler diagnostics always print the
  expanded structural type, never `N42` (errors 1, 2, 5 above). This is the
  single biggest ergonomic cost and there is no stable-Rust fix; it argues
  for keeping capacities small and for wrapping numbers in domain types
  whose *outer* name survives in errors (`BoltBox<...>` at least tells you
  what the number is counting).
- **Derived numbers have no aliases at all**: the result of `Pred`/`Add` is
  structural until unified with an alias, so intermediate states of a
  supplier show up as raw nests in any error they cause.
- **The alias table itself must be generated.** `macro_rules!` cannot mint
  identifiers, so `tools/gen_aliases.py` writes the 1001-line invocation
  lists. A one-off cost, but it is a build-process wrinkle the "just a
  macro" plan in the brief didn't anticipate.

## Candidate FINDINGS.md entries (ready to paste)

- **F1 — `macro_rules!` cannot generate the alias names `N0..N1000`.**
  What couldn't be expressed: a single macro invocation that *creates* 1001
  identifiers; stable `macro_rules!` can only consume identifiers it is
  given (no `paste`-style concatenation without a forbidden dependency).
  Cost: the alias names must literally exist in source. Workaround: a
  non-recursive macro (`nats!{ N0 => N1; N1 => N2; … }`) whose 1001-line
  invocation is written once by a small generator script
  (`experiments/exp01-type-level-numbers/tools/gen_aliases.py`); the macro
  is kept non-recursive so defining aliases costs no macro recursion depth.

- **F2 — Peano numbers need `#![recursion_limit ≈ N + 3]`, per crate.**
  What worked only with complications: using a Peano number bigger than
  ~125 (evaluating `VALUE` or solving `Add`/`Lt` bounds) exceeds the
  default recursion limit of 128; measured minimums were N+3 (503 for
  N=500, 1003 for N=1000). The attribute is per *crate*, so every model
  crate that touches deep numbers needs it, not just the numbers library;
  defining aliases alone stays lazy and needs nothing. Cost: a crate-level
  attribute and an E0275 error whose `help:` only suggests the next
  doubling. Workaround: set `#![recursion_limit = "2048"]` as project
  convention in any crate using type-level capacities.

- **F3 — Peano compile time is fine to N≈500, superlinear after.**
  Measurement (median of 3 clean debug builds, minimal crate, one `VALUE`
  use plus one addition): ~1.0 s at N=10/100, 1.6 s at N=500, 4.6 s at
  N=1000. Binary encoding stays ~1.1 s throughout with the default
  recursion limit (needs only bits(N)+3 ≈ 13 at N=1000). No blocker at the
  sizes R12 contemplates (boxes of 100), but a model using many distinct
  large Peano numbers would pay ~seconds per use-site cluster.

- **F4 — Binary decrement produces non-canonical types; a `Trim`
  normalisation pass is required.** What couldn't be expressed simply:
  `1000000000₂ - 1` naively yields `0111111111₂` — right VALUE, wrong
  *type* (a leading-zero form that fails type-equality against the
  canonical `111111111₂`; demo in
  `tests/compile_fail/dec_raw_not_canonical.rs`). Cost: extra `Trim` +
  `TrimmedCons` traits and a wrapper `Dec`; binary needed ~25 trait impls
  in all versus 7 for Peano, and internal helper names (`DecRaw`) leak into
  user-facing errors. Peano has no canonical-form problem by construction.

- **F5 — Type-level less-than is trivial in Peano, expensive in binary.**
  Peano `Lt` is two impls and worked first try, usable as a generic bound
  (`fn requires_lt<A: Lt<B>, B: Nat>()`). Binary comparison was not
  implemented: with the least-significant bit outermost, less-than needs a
  length comparison plus a most-significant-bit-first lexicographic pass
  (typenum-style `Cmp` machinery), judged not worth building for a stretch
  goal. If capacities ever move to the binary encoding, budget real effort
  for comparison.

- **F6 — Compiler errors erase aliases and never show decimal values.**
  A wrong number is always caught at compile time, but the diagnostic
  prints structural types: 40-deep `Succ` chains for Peano (count them to
  learn the number), compact but binary-only `UInt` forms for the binary
  encoding, and misleading primary lines like "expected `Zero`, found
  `Succ<Zero>`" (the diff after peeling common layers). Cost: modellers
  must decode types by hand; long types get spilled to
  `target/.../long-type-*.txt` files. Mitigations only: keep capacities
  small, wrap numbers in domain types whose outer name survives
  (`BoltBox<…>`), and rely on missing-trait errors (e.g. `Pred`/`Supply`
  not implemented for the empty state), which read far better than
  type-mismatch errors.

## Recommendation

**Adapt** — adopt Peano as the project's type-level numbers, with these
adaptations; keep the binary encoding on the shelf.

1. **Use the Peano encoding for R12 capacities.** The decisive argument:
   R12 stores supplier contents as a `Cons<H, T>` list, whose type is
   *already* O(N) deep — a binary counter alongside it saves no depth, no
   compile time, and no recursion limit. Peano's structure mirrors the list
   one-to-one (`Succ` ↔ `Cons`), its decrement is 2 impls with no
   canonicalisation traps, and less-than is trivial for capacity bounds.
2. **Set `#![recursion_limit = "2048"]` as a standing convention** in every
   crate that uses the numbers (F2), and document the E0275 error in the
   modeller's guide.
3. **Ship the aliases and the generator script** (F1); treat the generated
   files as source. Cap generated aliases at the realistic capacity scale
   (≤1000 is proven; compile time says stay ≤~500 per number where
   convenient, F3).
4. **Don't chase better mismatch errors — design around them** (F6): wrap
   counts in domain types and prefer trait-not-implemented shapes
   (`Supplier` not implemented for the empty box) over raw type equality;
   error 3 shows those read almost like the desired "the box is empty".
5. **Revisit the binary encoding only if** standalone numbers ≥ ~1000 with
   heavy arithmetic become necessary — it works (all criteria pass at
   N=1000 on the default recursion limit) but costs ~3× the machinery,
   needs `Trim` normalisation, and still lacks comparison (F4, F5).
